# Audit technique du projet

Date: 2026-03-25

## Périmètre

Audit centré sur le code source maintenable:

- Python applicatif
- Flask/WebSocket
- JS métier front
- templates Jinja
- tests et scripts de maintenance

Exclusions volontaires:

- assets binaires
- dépendances vendoriées/minifiées
- fichiers `.bak`
- caches, bases locales, logs, contenus de démonstration

## Fonctionnement actuel

Le projet démarre via `visualizer.py`, construit tous les composants avec `ComponentInitializer`, puis tourne dans une boucle temps réel qui:

- pilote l’état global (`StateManager`)
- lit les événements MIDI (`MidiPorts`, `MIDIEventProcessor`)
- applique les effets/fades (`LEDEffectsProcessor`)
- met à jour LED, écran LCD, idle animations et hotspot
- expose une interface web Flask + WebSocket

La persistance de configuration repose sur `config/settings.xml` via `UserSettings`. Le runtime du LED mapping repose surtout sur `LedSettings`, `LedStrip`, `ColorMode`, `functions.py` et `learnmidi.py`. L’interface web mélange aujourd’hui beaucoup de logique métier côté API (`views_api.py`) et côté JS (`ui.js`, `index.js`, `initialize.js`).

## Priorités de polissage

### P0

- Supprimer ou renommer `lib/.py`: fichier parasite de plus de 2000 lignes qui ressemble à une copie de `menulcd.py`, très risqué pour la maintenance.
- Découper `webinterface/views_api.py`: `change_setting()` est trop gros et devient une source de régression à chaque ajout.
- Découper `lib/functions.py` et `lib/menulcd.py`: les deux modules sont devenus des monolithes.
- Introduire une couche de validation centrale pour les settings au lieu d’éparpiller `int(value)`, conversions hex/rgb et bools dans les routes.
- Isoler les dépendances hardware dans les tests pour que `pytest` complet ne casse pas sur `spidev`.

### P1

- Passer les réglages vers des objets typés (`dataclass` / DTO) au lieu de chaînes XML partout.
- Extraire le front en modules plus petits avec un store global clair.
- Factoriser les templates répétitifs en macros Jinja.
- Ajouter des tests d’intégration API pour les changements de settings et les ports MIDI.

### P2

- Standardiser le style, la doc d’architecture et la stratégie de logs.
- Séparer clairement les fichiers de démonstration, de test matériel et de prod.
- Réduire la surface des fichiers statiques inclus côté client.

## Audit fichier par fichier

### Racine

- `visualizer.py`: bonne orchestration générale, mais la boucle principale garde encore trop de responsabilités. Extraire un orchestrateur de tick, un gestionnaire d’UI screen refresh et un gestionnaire d’activity/backlight rendrait le timing plus lisible et testable.
- `requirements.txt`: pinner précisément les versions critiques (`Flask`, `mido`, `websockets`, `psutil`) et séparer si possible les dépendances runtime des dépendances test/dev.
- `autoinstall.sh`: rendre le script strict (`set -euo pipefail`), idempotent, journalisé, et shellcheck-clean. Ajouter une détection claire Raspberry Pi / distro.
- `README.md`: très complet côté usage, mais il manque une vue architecture/code pour aider un mainteneur. Ajouter un schéma simple des flux MIDI/LED/web réduirait la courbe d’entrée.
- `CODE_OF_CONDUCT.md`, `LICENSE`: rien à optimiser côté code.
- `scripts/configure_rtpmidi_stability.sh`: ajouter `--dry-run`, vérification des commandes requises, sauvegarde des fichiers modifiés et logs d’exécution.

### Configuration

- `config/default_settings.xml`: fichier devenu long et peu structuré. Grouper logiquement les settings par domaine ou générer ce XML depuis une source typée éviterait les oublis.
- `config/menu.xml`: XML UI riche mais difficile à faire évoluer; prévoir des commentaires par bloc ou une doc miroir du menu LCD.
- `config/sequences.xml`: ajouter validation schéma + versioning léger pour détecter les presets incompatibles.

### Python `lib/`

- `lib/.py`: anomalie majeure. Fichier fantôme très volumineux, probablement doublon accidentel. À supprimer ou renommer immédiatement après vérification Git.
- `lib/__init__.py`: rien de particulier.
- `lib/animation_speed.py`: module utile et ciblé. Il gagnerait à exposer une API plus stricte avec types et exceptions dédiées au lieu d’inférer silencieusement certains formats.
- `lib/argument_parser.py`: simple, mais peut documenter mieux les modes/flags sensibles et centraliser les defaults dans une structure réutilisable.
- `lib/color_mode.py`: logique métier importante. La factory via `__new__` est pratique mais peu lisible; un registre explicite des modes serait plus maintenable. Le cache de notes mérite des tests dédiés.
- `lib/colormaps.py`: bon candidat à un service dédié. Ajouter cache disque/version, validation d’entrée et métriques de génération éviterait les recalculs silencieux.
- `lib/component_initializer.py`: rôle clair, mais couplage élevé. Retourner un conteneur structuré ou des sous-groupes (`io`, `ui`, `services`) aiderait.
- `lib/connectall.py`: beaucoup de shell parsing implicite. Ajouter une couche d’abstraction pour `aconnect` et mieux journaliser les échecs.
- `lib/functions.py`: dette technique majeure. C’est à la fois utilitaire, moteur d’animations, logique d’idle/screen saver et outils LED. À découper en modules `animations`, `color_utils`, `idle_logic`, `led_math`.
- `lib/gpio_handler.py`: correct mais très orienté effets de bord. Injecter la couche GPIO faciliterait les tests.
- `lib/LCD_1in3.py`: driver matériel acceptable; ajouter des guards plus clairs sur les erreurs SPI et documenter les timings.
- `lib/LCD_1in44.py`: même remarque; conserver ce type de fichier le plus proche possible du hardware, sans logique UI.
- `lib/LCD_Config.py`: isoler davantage les accès `spidev` / GPIO et prévoir un fallback de test pour éviter l’échec de collecte Pytest.
- `lib/learnmidi.py`: bloc métier critique et trop massif. `learn_midi()` doit être découpé en pipeline lisible: préparation, matching, scoring, envoi websocket, feedback LED.
- `lib/led_animations.py`: bonne direction avec un registre. Continuer en déplaçant progressivement les animations hors de `functions.py`.
- `lib/LED_drivers.py`: très petit; vérifier que l’API émulation reste strictement compatible avec le driver réel.
- `lib/led_effects_processor.py`: module sain. Extraire `pulse` dans un helper dédié si l’effet continue à grossir.
- `lib/ledsettings.py`: autre gros centre de dette. `set_sequence()` est trop longue; introduire des handlers par catégorie de setting et des conversions typées.
- `lib/ledstrip.py`: module compact et utile. Ajouter des tests sur changement de count/shift/reverse pour fiabiliser les reconfigurations à chaud.
- `lib/log_setup.py`: propre. Ajouter rotation optionnelle, format JSON optionnel et meilleure séparation console/fichier.
- `lib/menulcd.py`: monolithe UI majeur. À découper en rendu, navigation, édition de settings, widgets et thèmes. L’UI LCD est clairement devenue un mini framework sans frontières internes.
- `lib/midi_event_processor.py`: important et relativement bien structuré, mais encore trop centré sur des `if/elif` événementiels. Un dispatch par type de message simplifierait la lecture.
- `lib/midiport_resolver.py`: module bien ciblé. Ajouter plus de tests sur noms exotiques, RTP MIDI et ports bloqués.
- `lib/midiports.py`: sensible et complexe. Séparer découverte, connexion, callbacks, auto-reconnect et websocket bridge serait un gros gain de stabilité.
- `lib/null_drivers.py`: correct. Peut servir de base à un mode test plus officiel.
- `lib/platform.py`: très utile mais chargé. Scinder hotspot, wifi, timezone et adresse réseau en sous-services éviterait l’effet “couteau suisse”.
- `lib/profile_manager.py`: module globalement propre. Ajouter transactions explicites et index DB documentés.
- `lib/queue_utils.py`: simple et sain.
- `lib/rpi_drivers.py`: garder minimal. Ajouter doc sur le contrat attendu par le reste de l’app.
- `lib/savemidi.py`: correct, mais renforcer les validations de chemin/nom et les erreurs I/O.
- `lib/score_manager.py`: petit module; mérite des tests sur cas limites et normalisation des scores.
- `lib/state_manager.py`: bonne base. Les transitions d’état gagneraient à être formalisées dans une table claire ou un diagramme.
- `lib/usersettings.py`: cœur de persistance utile, mais tout est stringifié. Ajouter une API de lecture typée (`get_int`, `get_bool`, `get_json`) réduirait énormément la dette dans le reste du code.
- `lib/webinterface_manager.py`: correct. Ajouter gestion de cycle de vie plus explicite et meilleur reporting des erreurs de bind réseau.

### Backend web

- `webinterface/__init__.py`: mélange démarrage Flask, WebSocket, broadcast et état global. Extraire un module websocket dédié et une classe de service pour les clients practice/ledemu.
- `webinterface/views.py`: léger et lisible. Peut devenir encore plus simple si l’initialisation du thème et des routes statiques est factorisée.
- `webinterface/views_api.py`: principal point noir côté web. Plusieurs routes manipulent directement le runtime, le XML, le système et le shell. À refondre vers des endpoints plus petits avec services dédiés, validation d’entrée et schéma de réponse constant.

### Frontend JS

- `webinterface/static/index.js`: responsable de navigation AJAX, actions globales et settings. À découper en router léger + service API + navigation state.
- `webinterface/static/js/theme.js`: nouveau module utile. À garder petit; si la personnalisation grossit, passer sur un store de thème unique avec écouteurs déclaratifs.
- `webinterface/static/js/initialize.js`: beaucoup d’initialisation DOM par page. Remplacer les affectations manuelles par des binds plus modulaires réduirait les oublis. Le fix de chart resize/leak va dans le bon sens.
- `webinterface/static/js/ui.js`: très gros fichier métier front. À découper par domaine: ports, songs, presets, sequences, settings, practice. Aujourd’hui c’est le pendant front de `views_api.py`.
- `webinterface/static/js/profiles.js`: module utile mais assez volumineux; extraire l’accès API et le rendu DOM.
- `webinterface/static/js/notifications.js`: correct; prévoir une API plus uniforme pour niveaux, durée, stacking et accessibilité.
- `webinterface/static/js/number-input.js`: bonne idée; peut être mieux documenté et testé visuellement.
- `webinterface/static/js/files.js`: vérifier la cohérence avec `ui.js` pour éviter les doublons d’upload/download.
- `webinterface/static/js/metronome.js`: petit et ciblé; rien de critique.
- `webinterface/static/js/utils.js`: attention au syndrome “misc utils”; garder uniquement les helpers vraiment transverses.
- `webinterface/static/js/globals.js`: limiter au strict minimum; chaque global supplémentaire complique le debug.

### Templates Jinja

- `webinterface/templates/index.html`: shell principal trop chargé: layout, websocket, modal, scripts inline, logique de presets. Extraire les scripts inline et les blocs répétitifs.
- `webinterface/templates/home.html`: dashboard dense mais très répétitif. Factoriser les cartes statistiques/contrôles en macros ou includes.
- `webinterface/templates/ledsettings.html`: bon candidat à une décomposition plus fine, notamment pour les sections couleur/modes/brightness.
- `webinterface/templates/ledcolor.html`: très chargé en contrôles; passer par composants/macro de couleur éviterait les répétitions RGB/hex.
- `webinterface/templates/lightmode.html`: séparer mieux les modes pour éviter les champs cachés dispersés.
- `webinterface/templates/ledanimations.html`: vérifier la duplication potentielle avec la logique d’animation côté LED settings.
- `webinterface/templates/songs.html`: gros template; extraire table, toolbar, player et zones d’upload en sous-partials.
- `webinterface/templates/songs_list.html`: attention au couplage avec le JS de tri/recherche/profils.
- `webinterface/templates/sequences.html`: très orienté DOM impératif; un rendu plus data-driven serait plus robuste.
- `webinterface/templates/ports.html`: l’affichage des ports et connexions devrait être plus composantisé, surtout si l’UI visuelle continue d’évoluer.
- `webinterface/templates/network.html`: centraliser les blocs formulaire/statut pour homogénéiser l’UX.
- `webinterface/templates/practice.html`: l’iframe et le bridge websocket sont utiles, mais la logique inline est trop volumineuse pour un template.
- `webinterface/templates/sheet_music.html`: plutôt compact; vérifier surtout l’intégration et les responsabilités de script.

### CSS

- `webinterface/static/custom.css`: feuille devenue très longue avec couches historiques + UI moderne + overrides globaux. La scinder en `base`, `components`, `theme`, `utilities` serait un vrai gain.
- `webinterface/static/sheet_music.css`: garder strictement spécialisé notation/sheet.
- `webinterface/static/styles.css`: très simple; peut rester point d’entrée Tailwind.
- `webinterface/tailwind.config.js`: la `content` list est trop courte si le front continue de se modulariser. Prévoir une convention stable pour JS/templates.

### Tests

- `tests/test_usersettings.py`: bonne base; ajouter un test pour les nouveaux settings web theme et pour les conversions typées futures.
- `tests/test_logic.py`: utile mais encore trop limité pour les régressions de settings complexes.
- `tests/test_midiport_resolver.py`: le contenu est pertinent, mais l’exécution dépend de `PYTHONPATH`. Le packaging/test runner doit être normalisé.
- `tests/test_midiports_behavior.py`: étendre avec scénarios de reconnexion et websocket MIDI.
- `tests/test_screen.py`: aujourd’hui non portable à cause de `spidev`; à passer en test matériel marqué ou mocké.
- `tests/key_demo.py`, `tests/learnmidi.py`, `tests/lightkeys.py`, `tests/printmidimessages.py`, `tests/randomcolor.py`, `tests/strandtest.py`: ce sont davantage des scripts manuels que des tests. Les déplacer vers `examples/` ou `devtools/`.
- `tests/LCD_1in44.py`, `tests/LCD_Config.py`: à classer comme fixtures matérielles ou stubs, pas comme modules de test collectables.

## Recommandation d’ordre de refactor

1. Nettoyer les anomalies de dépôt (`lib/.py`, backups hors git, séparation scripts/tests/assets).
2. Introduire une couche de settings typés et de validation unique.
3. Découper `views_api.py`, `functions.py`, `menulcd.py`, `ui.js`.
4. Stabiliser les tests sans dépendances hardware obligatoires.
5. Factoriser les templates et le CSS en composants plus petits.
